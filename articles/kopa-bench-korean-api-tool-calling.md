## TL;DR

公開機関がオープンソースLLMエージェントをオンプレミスで運用するとき、複数の政府APIを連鎖的に呼び出すマルチステップのツール呼び出し能力が求められる。しかし、既存ベンチマークはどれも「真の公開APIに対する連鎖呼び出し」を測っていない。本論文は、145の実タスクからなる**KOPA-Bench**（韓国公開APIベンチマーク）を構築し、同時に**EDGE**（Execution-grounded Dynamic Graph for tool-calling data synthEsis）というデータ合成手法を提案する。EDGEは、LLMの事前判断だけでなく実際のAPI呼び出し結果で依存グラフを検証・剪定し、実行可能なマルチステップ軌跡を合成する。GRPOで微調整した**Qwen3.5-9B**は、同じファミリの無調整27Bにほぼ匹敵する性能を達成し、分布外のBFCLベンチマークでも一貫して改善した。

## 背景

### データ主権とオンプレミスエージェント

韓国をはじめとする多くの国で、データ主権規制により公共機関はLLMエージェントをクラウドではなくオンプレミスで運用しなければならない。となれば、選択肢はオープンソースモデルに限られる。しかし、オープンソースモデルはGPT-5やClaudeといった専有モデルに比べ、特に**複数のAPIをまたぐ多段ツール呼び出し**で大きく劣る。

### 既存ベンチマークの限界

関数呼び出し能力を評価するベンチマークは既にいくつか存在する。BFCLは主に単一ステップか単純な多段に留まり、実際のAPIを使わない。ToolBenchは数千のREST APIを対象とするが、エンドポイントの安定性に難がある。StableToolBenchは模擬環境で安定性を確保したものの、本物のAPIではない。τ²-Benchはユーザーシミュレータで評価するが、やはり公開APIではない。

要するに、「**本物の政府APIエンドポイントに対する連鎖的なマルチステップ呼び出し**」を評価するベンチマークが存在しなかった。

## 方法详解

### KOPA-Bench：韓国公開APIベンチマーク

KOPA-Benchは、10の韓国政府公開プラットフォーム、6つの領域（交通・金融・教育・法律・政治・行政区画）にまたがる145の実タスクからなる。特徴的な統計量を以下に挙げる。

- 平均所要ツール呼び出し回数：**4.92回**（最大14回）
- 平均推論ステップ数：3.32ステップ
- 並列実行を含むタスクの割合：59%
- 平均利用可能ツール数：7.5
- 総ツールインベントリ：**2,318関数**（すべて実際のAPIエンドポイントに裏打ち）

各ツールはMCP（Model Context Protocol）サーバとして実装され、認証・セッション管理・エラーハンドリング・リトライロジックを統合している。

#### 三次元評価手法

単なる最終回答の一致だけでなく、以下の3軸で評価する。

1. **RESPONSE**：最終回答が実値と一致するか（String / Number / Judgeの3型）
2. **ENVIRONMENT**：ツール実行後のシステム状態をSHA-256ハッシュで比較
3. **ACTION**：ツール呼び出し軌跡の正確性と効率性
   - 正確性 Corr = 黄金動作に一致した割合
   - 効率性 Eff = (重複呼び出し比CR + 最短経路被覆MPC) / 2
   - ACTION = (Corr + Eff) / 2

![図1: KOPA-Benchの領域別タスク分布と主要統計量](/images/kopa-bench-korean-api-tool-calling/fig1.png)

#### タスクの具体例

金融領域の例：「Lightron Fiber-optic Devicesが2026年1月に発行した転換社債を参照し、昨日の終値と再価格設定下限のパーセント差を計算せよ。」

黄金軌跡は次の4ステップからなる。

1. `find_dart_corp_code(company_name="Lightron")` → 企業コード "00367482"
2. `get_dart_convertible_bond_issuance_decision(corp_code="00367482", ...)` → 再価格設定下限 532
3. `get_stock_price_trend(ticker="069540", ...)` → 終値 1680
4. `evaluate_expression("100 * (1680 - 532) / 532")` → 215.78...

このように、前ステップの出力が次ステップの入力に流れる**連鎖依存**が本ベンチマークの本質である。

### EDGE：実行錨定動的グラフによるデータ合成

EDGEは、真のAPI呼び出しで検証された依存グラフからマルチステップ軌跡を合成する二段階フレームワークである。

#### Phase A：実行錨定動的グラフの構築

**ステップ1：骨格グラフ構築**

2,318個のツールをノードとする有向依存グラフ $G = (V, E)$ を構築する。

1. 候補辺選択：密検索器で署名埋め込み、各ソースツールにつき域内top-15 + 域外top-10の近傍に限定
2. LLM実現性採点：各候補辺について、LLMが実現性スコア $s_e \in [0,1]$、束縛セット $B_e$（下流パラメータ→上流出力の対応）、デフォルト候補 $D_e$ を返す
3. パラメータ源計画 $\Pi_e(p)$：各パラメータを Upstream / Default / Clarify のいずれかに分類
4. $s_e \geq 0.3$ の辺のみ採用、採用辺にはBeta事前 $\alpha_e = 1 + \kappa \cdot s_e$、$\beta_e = 1 + \kappa \cdot (1 - s_e)$（$\kappa=2.0$）を付与

**ステップ2：実行錨定グラフ更新**

100回の反復（各回500経路サンプリング）で、Thompson標本化で辺を選択し、実際にAPIを呼び出して結果を分類する。

| 結果種別 | グループ | 事後更新量 |
|---------|---------|-----------|
| 意味的成功 | — | $\alpha_e += 1.0$ |
| 汎用パラメータのみ成功 | — | $\alpha_e += 0.3$ |
| スキーマ/型不一致 | 構造的 | $\beta_e += 1.5$ |
| フィールド欠落 | 構造的 | $\beta_e += 1.0$ |
| レート制限 | 環境的 | $\beta_e += 0.1$ |
| タイムアウト | 環境的 | $\beta_e += 0.3$ |
| サーバエラー | 環境的 | $\beta_e += 0.3$ |

ここでの設計上の肝は、**構造的失敗と環境的失敗を峻別**している点だ。ランダムなサーバエラーで正しい束縛を持つ辺を過度に罰してはならない。逆に、型が合わない等の構造的欠陥は重く罰する。

$n_e \geq n_{\min}$ かつ $\Pr[\theta_e > \tau_{\text{prune}}] < \varepsilon_{\text{prune}}$ を満たす辺を剪定する。

**結果**：骨格グラフの辺実行成功率50.2% → 収束グラフ $G^*$ で62.7%（+12.5pp）。剪定された辺の成功率はわずか14.8%であり、剪定の精度を裏付ける。

![図2: EDGEの実行錨定動的グラフの精度改善プロセス](/images/kopa-bench-korean-api-tool-calling/fig2.png)

#### Phase B：型に基づく軌跡合成

収束グラフ $G^*$ に基づき、ツール呼び出し連鎖 $(T_1, \ldots, T_m)$ を合成する。ここで特有な挑戦は、韓国公開APIがしばしば**数千件のレコード**を返すことだ。単一値を仮定する既存手法では対応できない。

そこで、各ノードの返却件数 $n_i$ に応じて3種に分類する（fan-out予算 $\phi=5$）。

- **Sequential (Seq)**：$n_i = 1$。単一値をそのまま次ツールに渡す
- **Fan-out (Fan)**：$2 \leq n_i \leq \phi$。各値について下流呼び出しを発行
- **Derived (Drv)**：$n_i > \phi$。内部処理ノードを挿入し、max/min/フィルタ等で有界部分集合を選択

さらに、順序軌跡以外にも、意味的並列（Sem）・比較（Cmp）・条件分岐（Cond）の非順序テンプレートを合成する。

**三段階検証パイプライン**：

1. 規則フィルタ：非再現インスタンス・エラーデータ・近重複・形式異常を除去
2. LLM静的フィルタ：非評価可能クエリ・回答漏洩クエリ・装飾的連鎖を除去
3. 独立再解：各タスクを再求解し、正しいものは元の回答を置換

**重要原則**：訓練ラベルにはオープンソースモデル出力のみを用い、専有モデルは検証にのみ用いる。データ汚染を回避するためだ。

最終的に1,781の合成タスクが得られ、平均4.13回呼び出し、57.6%が4以上の順序跳躍を含む。

### GRPOによる微調整

合成データセットでGRPO（Group Relative Policy Optimization）により微調整する。SFTが単一参照軌跡を模倣するのに対し、GRPOは複数ロールアウトの相対報酬から学習する。有効な軌跡が複数存在する場合、GRPOはより多くの信号を抽出できる。

## 実験結果

### KOPA-Bench主結果

![図3: KOPA-Benchにおけるモデル性能比較](/images/kopa-bench-korean-api-tool-calling/fig3.png)

専有モデルではClaude Sonnet 4.6がpass@1 0.4655で首位。オープンソース大型ではQwen3.5-27Bが0.4482と健闘。

EDGE+GRPOで微調整したモデルの結果が注目すべきだ。

- **Qwen3.5-9B**：pass@1 0.3275 → **0.4310**（+10.3pp）。これは無調整のQwen3.5-27B（0.4482）にほぼ匹敵する。パラメータ1/3で27Bに肉薄したことになる。
- **Qwen3.5-4B**：pass@1 0.1758 → **0.3094**（+13.4pp）。4Bモデルが微調整なし9B（0.3275）に迫る改善幅。

95%信頼区間が重複せず、統計的に有意である。

### BFCLベンチマーク（分布外汎化）

KOPA-Benchで訓練したモデルが、全く異なるツール宇宙のBFCLでも改善するか。

- Multi-Turn：4B +4.04pp、9B **+5.87pp**と最も顕著
- 訓練データは主に単一ラウンドだが、多段ツール呼び出し軌跡の構造が多回対話の構造と整合するため、汎化が生じる

### 未見プラットフォームでの評価

31の未見小売プラットフォームタスクで、4Bのpass@4が0.2903 → **0.5161**（+22.6pp）。全ベンチマークの最大改善幅+15.9ppを上回り、EDGEの合成データがプラットフォームを越えて汎化することを示す。

## 考察

### SFT vs GRPO：データか、目的関数か

SFT単独でpass@1 +9.7ppの改善があり、**大部分の向上はデータセットに帰着**する。GRPOはSFTを基にさらにpass@4で+11.0ppの追加改善をもたらす。SFTが教師の単一軌跡に上限を制限されるのに対し、GRPOは複数ロールアウトの相対順位から学習できるためだ。

結論として、**良質なデータが第一義**であり、訓練目的関数はその上で磨きをかける役割である。

### 軌跡多様性の相補性

pure-sequentialのみの訓練ではpass@1 0.2327に留まる。並列テンプレートを加えると0.3080に跳ね上がる。full設定はpass@4でさらに0.4690に達する。順序軌跡は出力-入力の受け渡しを教え、並列軌跡は比較・条件パターンを注入する。二つは相補的である。

### 実行錨定の本質

「ループは、稼働APIが拒否する辺を正確に除去する。実行せずに依存を固定するいかなるパイプラインも、これを検出できない。」

この一文がEDGEの存在意を凝縮している。LLMの事前判断だけでは50.2%の辺しか実行可能でなかったものが、実行証拠の蓄積により62.7%に向上し、同時に失敗辺を14.8%に特定して剪定した。**実行が嘘を見抜く**、その仕組みこそがEDGEだ。

### データ汚染の不在

訓練と評価のツール宇宙は62.2%重複する（同じAPIプールを共有するため当然）。しかし、関数対レベルの依存辺重複（Jaccard）は0.000、隣接辺未見率は95.6%である。同じツールを使うが、**つなぎ方が全く異なる**——これがデータ汚染の定義から外れる理由である。

## 関連研究

### 関数呼び出しベンチマーク

API-Bankは基礎的で規模が小さい。BFCLは単一・単純多段が中心で実際のAPIを使わない。ToolBenchは実REST APIだが不安定。StableToolBenchは模擬環境で安定性を確保したが本物ではない。τ²-Benchはユーザシミュレータで評価するが公開APIではない。

KOPA-Benchは、**真の公開APIに対する連鎖依存呼び出し**を評価する唯一のベンチマークである。

### 関数呼び出しデータ合成

ToolACEは検証段を追加するが単一値返却を仮定する。AWMは模擬API環境で生成する。MagnetとBUTTONは署名やLLM計画で関数を連結するが、**実際の実行を検証しない**。APIGen-MTも同様に単一結果返却を仮定する。

EDGEは3点で差別化される。(1) 実行錨定：各依存辺を実際のAPI呼び出しで検証。(2) 高カーディナリティ処理：Seq/Fan/Drvの3種で数千件返却に対応。(3) 動的グラフ：事後分布とトポロジーが実行証拙の蓄積とともに変化する。

## まとめ

KOPA-Benchは、真の韓国政府APIに対するマルチステップツール呼び出し能力を測る初のベンチマークであり、EDGEはそのギャップを埋めるデータ合成手法である。EDGEの核心は、LLMの事前判断だけでなく実際のAPI呼び出しで依存グラフを検証・剪定する「実行錨定」にある。構造的失敗と環境的失敗を峻別し、Thompson標本化で探索と搾取を均衡しながら、実行可能な辺だけを残す。GRPOで微調整した9Bモデルは27Bにほぼ匹敵し、分布外のBFCLや未見プラットフォームでも一貫した改善を示した。データ主権の時代に、オープンソースモデルが実APIを介した複雑な推論でどこまで迫れるか──その答えの一端を本論文が示している。
