# 読むことと推論を分ける──PARSERが長文脈Agentの並列読みと深い推論を両立する仕組み

> **PARSER: Read in Parallel, Reason in Depth for Long-Context LLM Agents**
> Kun Li, Zexuan Qiu, Tianhua Zhang, Irwin King, Helen Meng
> arXiv:2609.06702 (2026年9月)

## TL;DR

長文脈を扱うLLMエージェントの多くは、文書を順次読みながら圧縮記憶を更新していく──いわゆる sequential memory agent だ。だがこのやり方では、**証拠が文書のどこにあるか**で精度が大きく揺らぎ、文書が長くなるほど推論遅延も線形に膨らむ。PARSERはここを根本から切り替える。複数の軽量サブエージェントが文書をチャンクごとに**並列**で読み、リードエージェントが**反復的に問いを深めて**推論する──読みと推論を解耦することで、896Kトークンでも精度はほぼ平坦、遅延は最大11分の1に抑えられた。4Bモデルで既存の最強メモリベースラインを平均+5.7点上回り、9BにスケールするとDeepSeek-V4-Proを+6.3点で凌駕する。

## 背景：順次読みの瓶颈

長文書を扱うエージェントは、これまで主に二系統のアプローチに分かれてきた。

**Full-Context**は文書全体をコンテキスト窓に詰め込む方式。短い文書では強いが、コンテキストが長くなると注意力が希薄になり（いわゆる lost-in-the-middle）、896Kトークンでは4Bモデルの精度が31%まで崩れ落ちる。

**Sequential Memory Agent**（MemAgent, ReMemR1 など）は、文書をチャンクに切り、1チャンクずつ読みながらメモリ状態を更新していく。メモリは固定サイズのベクトルやテキスト要約で、読み進めた情報を圧縮して保持する。この設計には三つの構造的瓶颈がある。

1. **証拠位置への感応性**：証拠が文書の前・中・後ろのどこにあるかで精度が激しく変動する。メモリは「最近読んだチャンク」の情報を保ちやすいが、遠い過去のチャンクに含まれる証拠は忘れられやすい。
2. **証拠順序への感応性**：論理的に後で使うべき証拠が先に現れると、メモリに収めた時点でその後の推論文脈が失われており、正しいつなぎ合わせができない。
3. **証拠距離への感応性**：二つの証拠の間に大量の無関係段落が挟まると、一方を読んだ時点でもう一方の情報がメモリから退勢している。

これら三つはすべて、**読む順序（文書が決める）**と**推論する順序（問題が決める）**が同一のトラバーサルに絡め取られていることに起因する。PARSERの出発点はこの絡み合いを解くことだ。

![HotpotQAにおけるコンテキスト長と精度の関係](/images/parser-parallel-reading-sequential-reasoning/fig1.png =800x)
*図1: HotpotQAにおけるコンテキスト長と精度。Full-Contextは長文脈で急激に劣化し、Sequential Memoryも漸次低下する一方、PARSERは7K〜896Kまでほぼ平坦に推移する。*

## 方法：Scatter–Gatherで読みと推論を解耦

### 設計思想

PARSERの核心は一文に集約できる。

> **文書の読み順は文書が決める。推論の進め順は問題が決める。この二つを同じトラバーサルに押し込むから瓶颈が生じる──だから解く。**

具体的には、文書長を「順次の深さ」ではなく「並列の幅」に変換する。文書を$T$個のチャンクに分け、$T$個のサブエージェントが各1チャンクを担当して並列に読む。リードエージェントは一切の生テキストに触れず、サブエージェントから集めた証拠だけを頼りに推論を深めていく。

![PARSERのScatter–Gatherアーキテクチャ](/images/parser-parallel-reading-sequential-reasoning/fig2.png =800x)
*図2: PARSERのScatter–Gatherアーキテクチャ。各ラウンドでリードエージェントが問いを放送（Scatter）し、全サブエージェントが並列で証拠を探索して返信（Gather）する。*

### Scatter–Gatherの反復

各ラウンド $k = 1, 2, \ldots, K$ で次が起きる。

1. **Scatter**：リードエージェントが現在の推論状態に基づいて聚焦クエリ $q_k$ を生成し、全サブエージェントに放送する。
2. **Gather**：各サブエージェントは自分のチャンク内で $q_k$ に関連する証拠を探し、見つかれば返し、見つからなければ短い放棄応答（abstain）を返す。リードエージェントは全サブエージェントからの応答を集約する。
3. **推論の深化**：集めた証拠に条件化して、より深い次のクエリ $q_{k+1}$ を構成する。マルチホップQAなら「第一ホップの答えを使って第二ホップを問う」という形で自然に深まっていく。
4. 最終ラウンドでリードエージェントが答えを提出するか、上限 $K$ に達したら停止。

### 設計がもたらす性質

| 性質 | 説明 |
|------|------|
| **対称アクセス** | 同一ラウンド・同一クエリのもとで全チャンクが並列に検査される。位置による特権なし。 |
| **再訪可能性** | ラウンドごとに新クエリで全チャンクを再検査できる。一度見たからといって永久に破棄しない。 |
| **跨チャンク依存の解決** | 複数ホップにまたがる依存は、推論ラウンドをまたぐ条件化クエリ連鎖で解く。文書順のメモリ伝播に頼らない。 |
| **疎な通信** | 多くのサブエージェントは放棄応答のみ返し、デコード計算は最小。 |
| **遅延の解耦** | クリティカルパスは推論深さ $K$ ラウンドであり、文書長 $T$ には依存しない。 |

### 学習：リードエージェントのみRL

PARSERの学習対象はリードエージェントだけだ。サブエージェントは凍結した既存モデル（Qwen3.5-4B）をそのまま使う。リードエージェントの最適化には GRPO（Group Relative Policy Optimization）+ RLVR（Verifiable Reward）を用いる。報酬は二元完全一致スコア $r = \mathrm{EM}(a_{\mathrm{pred}}, a_{\mathrm{gold}})$ のみ。サブエージェントからの観測トークンは報酬の因果経路に含めない（遮蔽）ため、方策勾配はリードエージェントの生成トークンにのみ適用される。

この設計の利点は二つ。一つは訓練コストが文書長に依存しないこと──リードエージェントのロールアウトは推論ステップ数 $K$ に比例し、チャンク数 $T$ には無関係だ。もう一つはサブエージェントを差し替え可能なこと──後述する通り、thinkingサブエージェントやDCIサブエージェントに差し替えてもリードエージェントの再訓練なしで同等の性能が出る。

## 実験結果

### メイン評価：HotpotQA（域内）

HotpotQAは2ホップの質問応答ベンチマーク。文脈長を7K〜896Kトークン（50〜6400段落）に変動させて評価した。

| 方法 | 骨干 | 7K | 56K | 224K | 896K | **平均** |
|------|------|-----|-----|------|------|--------|
| Full-Context (think) | 4B | 80.5 | 76.6 | 60.9 | 31.3 | 65.8 |
| MemAgent | 4B | 81.3 | 77.9 | 79.7 | 72.9 | 78.6 |
| ReMemR1 | 4B | 82.0 | 78.9 | 80.0 | 73.4 | 78.9 |
| **PARSER** | **4B** | **85.7** | **85.7** | **83.1** | **85.4** | **84.6** |
| DeepSeek-V4-Pro | — | 82.0 | 80.5 | 81.3 | 78.9 | 80.5 |
| **PARSER** | **9B** | **86.7** | **85.7** | **86.7** | **85.9** | **86.8** |

PARSER (4B) は最強のsequential memory基線（ReMemR1）を平均で+5.7点上回り、896Kでは差が+12.0点に開く。9Bにスケールすると、DeepSeek-V4-Pro（100万トークン対応の商用モデル）を+6.3点で凌駕する。

注目すべきはPARSERの**長さ不変性**だ。7Kでも896Kでも精度は83〜86%の狭い帯域に収まる。一方、Full-Contextは80%から31%まで急落し、MemAgentも84%から73%まで漸次低下する。

### 域外汎化：2WikiMultiHopQA

| 方法 | 骨干 | 平均 |
|------|------|------|
| DeepSeek-V4-Pro | — | 88.2 |
| MemAgent | 4B | 60.6 |
| ReMemR1 | 4B | 77.4 |
| **PARSER** | **4B** | **87.0** |
| **PARSER** | **9B** | **88.5** |

MemAgentとReMemR1は域外で大幅に劣化するが、PARSERはほぼ健在だ。読みと推論を解耦しているため、リードエージェントが学ぶのは「問題をどう段階的に解くか」という汎用的推論能力であり、訓練文書の特定の要約パターンではない──と著者らは分析している。

## 考察

### 証拠分布に対するロバスト性

制約実験で三つの次元──証拠位置・証拠順序・証拠間距離──を独立に操作した。

![証拠分布ロバスト性の比較](/images/parser-parallel-reading-sequential-reasoning/fig3.png =800x)
*図3: 証拠位置・順序・距離を操作した制約実験。MemAgentとReMemR1はいずれかの条件下で大幅に劣化するが、PARSERは三次元すべてでほぼ平坦。*

- **証拠位置**：MemAgentは50〜70百分位（文書中盤）で顕著に低下。PARSERはほぼ平坦。
- **証拠順序**：論理依存順を反転させると、MemAgentは約20点、ReMemR1は約16点落ちる。PARSERは1点差で安定。
- **証拠間距離**：二つの証拠の間に無関係段落を挟むほどMemAgent・ReMemR1は悪化するが、PARSERは影響を受けない。

この三つのロバスト性はすべて、全チャンクが各ラウンドで同時に検査され、推論クエリに基づいて動的に再訪できるというPARSERの設計から直接帰結する。

### 推論遅延の削減

![896Kコンテキストでの推論遅延](/images/parser-parallel-reading-sequential-reasoning/fig4.png =800x)
*図4: 896Kコンテキストにおける推論遅延。並列度1でMemAgent 876秒に対しPARSER 78秒（11倍高速化）。*

896Kトークンの推論遅延を測定した。並列度1（サブエージェントを直列実行）でも、PARSERは78秒でMemAgentの876秒に対し11倍の高速化を達成する。これはPARSERの推論ステップ数が推論ホップ数 $K$（通常3〜5）に比例し、チャンク数 $T$（896Kなら数百）に比例しないからだ。並列度16では58.86秒まで縮むが、KV-cache退勢によるリプリフィルのオーバーヘッドで理想比には達しない。

### サブエージェントのサイズと差し替え

サブエージェントを2B・4B・9Bに変えて実験したところ、4Bから9Bへの向上はわずか0.2点でほぼ飽和した。サブエージェントのタスク（短いチャンク内でクエリに関連する部分を特定する）は難しくなく、4Bで十分という結果だ。

さらに、凍結サブエージェントの実装を差し替えてもリードエージェントの再訓練なしで性能が保たれることを確認している。thinkingサブエージェント（推論トークンを出力するモデル）やDCIサブエージェント（document-context inference専用モデル）に差し替えても、それぞれ85.6%・84.7%と、デフォルトの4Bサブエージェント（84.6%）と同等かそれ以上の性能が出る。リードエージェントが学んだのは「どう問いを生成し、どう集めた証拠を統合するか」という協調プロトコルであり、サブエージェントの内部実装の詳細には依存しない。

### 強化学習の寄与

RLなしのPARSERはHotpotQA平均74.4%で、RLあり（84.6%）と比べると約10点の差がある。ただし、RLなしでもMemAgent（78.6%）やReMemR1（78.9%）を下回るわけではない──骨干モデルが備える多段ツール呼び出しのネイティブ形式だけでかなりの性能が出る。RLはそれをさらに押し上げる。

### チャンクサイズの影響

チャンクサイズを4K・16K・64K・128K・全文（分块なし）で比較した。4Kが最も良く（平均84.6%）、チャンクが大きいほど性能が低下し、全文一括では73.8%まで落ちる。これは context rot 現象の影響で、長いチャンクでは後半のトークンへの注意力が減衰する。短いチャンクへの分割がこの減衰を緩和する。

## 関連研究

**Sequential Memory Agent**（MemAgent, ReMemR1, ReadAgent など）は、文書を順次読みながらメモリを更新する系統。PARSERはこの系統の構造的前提──読みと推論の同一トラバーサル──を問い直す。

**RAG / Retrieval-Augmented Generation** は文書から関連部分を検索してコンテキストに追加する。PARSERとの違いは、RAGが通常1回の検索で終わるのに対し、PARSERは推論の深化に伴って複数ラウンドで動的にクエリを変えながら再検索する点にある。また、RAGの検索はベクトル類似度に基づくことが多いが、PARSERのサブエージェントは言語理解能力を使ってチャンク内の証拠を特定する。

**MAPLE / StreamBench** などは長文脈ベンチマークの整備に貢献したが、エージェントの設計そのものには踏み込んでいない。

**Multi-Agent LLM**（CrewAI, AutoGen など）は複数エージェントの協調を探るが、読みと推論の解耦というPARSERの具体的設計原理には触れていない。

## まとめ

PARSERが示したのは、長文脈エージェントの瓶颈が「文書の読み順」と「問題の推論順」の絡み合いにあるということ、そしてその解決策が並列読みと反復推論の解耦にあるということだ。解耦がもたらす利点は三つに整理できる。

1. **ロバスト性**：証拠の位置・順序・距離のいかなる摂動に対してもほぼ不感。Sequential memoryが苦手とする「真ん中にある証拠」や「逆順の証拠」を問題にしない。
2. **効率**：推論遅延が推論複雑度（ホップ数）に比例し、文書長に無関係。896Kトークンで11倍の高速化。
3. **簡潔な訓練**：リードエージェントのみRLで訓練し、サブエージェントは凍結。訓練コストは文書長に依存せず、サブエージェントの差し替えも再訓練なしで可能。

4BモデルでSequential Memoryの最強基線を+5.7点、9BでDeepSeek-V4-Proを+6.3点上回るという結果は、読みと推論を分けることが単なる設計の好みではなく、構造的な優位性であることを強く示唆している。
